CHAPTER 1: INTRODUCTION

1.1 Background

In the contemporary digital era, instant communication platforms have evolved from optional messaging utilities into mission-critical infrastructure for modern web applications, enterprise collaboration tools, and social networks. The demand for low-latency, real-time messaging services capable of transmitting multimedia content securely and reliably across diverse device ecosystems has risen exponentially. Traditional web architectures relying exclusively on request-response HTTP polling models introduce significant latency overheads, unnecessary network bandwidth consumption, and sub-optimal user experiences when handling continuous bi-directional messaging.

To overcome the limitations of classic HTTP communication, modern web development leverages event-driven architectures powered by WebSockets. The WebSocket protocol establishes a persistent, full-duplex TCP connection between the client browser and the application server, allowing data to be pushed instantaneously in both directions with minimal protocol header overhead. Combining WebSocket engines with asynchronous server-side runtimes, flexible NoSQL document stores, and reactive single-page frontend frameworks enables software engineers to construct scalable, interactive real-time applications.

The MERN stack—comprising MongoDB, Express.js, React.js, and Node.js—represents a dominant full-stack paradigm for modern JavaScript application development. By utilizing JavaScript across all operational layers (client interface, server business logic, database queries, and real-time socket events), developers achieve high execution velocity, seamless code reuse, and unified data representation. This industrial training project focuses on designing, implementing, testing, and deploying a production-grade MERN-stack real-time messaging application named Chatters.

1.2 About the Project

Chatters is a feature-rich, full-stack real-time messaging platform designed to facilitate instant peer-to-peer text communication, multimedia content distribution (image sharing), and dynamic user presence tracking. Built from the ground up using the MERN architecture, Chatters integrates robust backend RESTful APIs, an event-driven Socket.io communication engine, secure HTTP-only JSON Web Token (JWT) authentication, Cloudinary cloud media storage, and a highly responsive React single-page frontend styling system powered by Tailwind CSS and DaisyUI.

The system provides authenticated users with an intuitive, unified dashboard consisting of an active sidebar displaying registered community members alongside live online presence indicators, an interactive chat window featuring scroll-managed message history, instant image upload previews, customizable user profile avatars, and dynamic UI theme selection supporting 32 distinct aesthetic configurations (e.g., dark, light, synthwave, dracula, cyberpunk). The platform is architected with a decoupled modular structure, separating application state management (Zustand), network transport (Axios and Socket.io-client), database persistence (Mongoose ODM), and server-side route protection.

1.3 Motivation

The primary motivation behind undertaking the development of Chatters during the summer industrial training was to gain hands-on engineering experience in solving complex full-stack architectural challenges. Specifically, the project aimed to address several critical software engineering objectives:

  • Real-Time Systems Engineering: Mastering real-time bi-directional networking protocols using Socket.io to achieve sub-second message delivery latency between connected clients.
  • Security & Session Management: Designing secure authentication workflows using JWT stored in HTTP-only cookies, combined with bcryptjs password hashing and Mongoose schema validations.
  • Cloud Media Storage Integration: Integrating third-party cloud storage APIs (Cloudinary) for base64 media encoding, image uploading, and CDN asset management.
  • State Management Optimization: Architecting lightweight, centralized client-side state stores using Zustand to manage asynchronous HTTP API requests, active WebSocket event listeners, dynamic UI theme persistence, and online user lists.
  • Component-Based UI/UX Design: Developing modern, responsive, and visually appealing user interfaces using Tailwind CSS and DaisyUI with support for extensive theme switching capabilities.

CHAPTER 2: PROBLEM STATEMENT

Conventional web-based messaging systems frequently suffer from performance bottlenecks, security vulnerabilities, poor multi-device usability, and clumsy user interfaces. Understanding these operational limitations is essential for architecting a superior solution. The specific engineering challenges addressed by the Chatters project include:

  • 1. High Communication Latency & Polling Overhead: Traditional HTTP short-polling or long-polling implementations create high network overhead, server CPU strain, and perceptible delivery delays (latency) when exchanging messages between users.
  • 2. Vulnerable Authentication & Session Management: Storing JWT authentication tokens in local storage or session storage exposes applications to Cross-Site Scripting (XSS) attacks. Furthermore, unauthenticated WebSocket handshakes allow unauthorized clients to establish socket connections.
  • 3. Inefficient Multimedia Handling & Cloud Storage: Handling direct multimedia uploads on server local filesystems causes scaling issues, storage disk exhaustion, slow response times, and broken asset links during cloud deployment.
  • 4. Unreliable Presence Tracking & State Synchronization: Tracking online/offline user states across distributed client sessions without dedicated socket connection maps results in stale online indicators, missed socket broadcasts, or memory leaks.
  • 5. Lack of UI Personalization & Responsive Layouts: Many web applications lack UI responsiveness across mobile and desktop displays or fail to offer user personalization options such as dynamic theme customization, resulting in rigid and uninspiring user experiences.

To resolve these challenges, there exists an immediate technical requirement for an integrated, secure, real-time messaging architecture. The proposed Chatters platform directly addresses these issues by deploying a Socket.io WebSocket engine for instant bi-directional messaging, enforcing HTTP-only cookie-based JWT authentication, integrating Cloudinary cloud asset management, maintaining an active socket mapping table for accurate presence detection, and implementing a 32-theme responsive React interface.

CHAPTER 4: TECHNOLOGIES AND CONCEPTS USED

4.1 Node.js and Express.js

Node.js is an asynchronous, event-driven JavaScript runtime built on Chrome's V8 engine. It enables server-side execution of JavaScript code, utilizing a non-blocking I/O model that renders it highly efficient for real-time, data-intensive applications. Express.js is a minimal and flexible Node.js web application framework that provides a robust suite of features for building single-page, multi-page, and hybrid web applications. In the Chatters architecture, Express.js (v5.1.0) handles API routing, middleware execution (cors, cookie-parser, JSON body parsing), and serves as the HTTP foundation for the Socket.io server.

4.2 RESTful APIs

Representational State Transfer (REST) is an architectural style for designing networked applications. RESTful APIs utilize standard HTTP request methods (GET, POST, PUT, DELETE) to execute operations on resources identified by URIs. In Chatters, REST endpoints were developed for user authentication (/api/v1/auth/signup, /api/v1/auth/login, /api/v1/auth/logout, /api/v1/auth/check, /api/v1/auth/update-profile) and message management (/api/v1/messages/users, /api/v1/messages/:id, /api/v1/messages/send/:id).

4.3 MongoDB and Mongoose ODM

MongoDB is a source-available, cross-platform document-oriented NoSQL database. Rather than storing data in rigid tables and rows, MongoDB utilizes flexible JSON-like documents with dynamic schemas (BSON format). Mongoose (v8.17.0) is an Object Data Modeling (ODM) library for MongoDB and Node.js. It manages relationships between data, provides schema validation, and translates between code objects and database documents. Mongoose schemas were defined for User collections (email, fullName, password, profilePic) and Message collections (senderId, receiverId, text, image, timestamps).

4.4 Socket.io for Real-Time Communication

Socket.io is an event-driven library that enables real-time, bi-directional, and low-latency communication between web clients and servers. It automatically selects the optimal transport protocol—upgrading from HTTP long-polling to WebSockets when supported. In Chatters, Socket.io (v4.8.1) manages WebSocket handshakes, maintains an in-memory userSocketMap key-value object mapping user IDs to socket IDs, broadcasts live getOnlineUsers arrays to all connected clients, and emits targeted newMessage events directly to recipient socket channels.

4.5 React.js and Vite Framework

React.js (v19.1.0) is a declarative, efficient, and flexible JavaScript library for building component-based user interfaces. It utilizes a Virtual DOM to optimize rendering performance by minimizing direct DOM manipulations. Vite (v7.0.4) is a next-generation frontend build tool that provides fast Hot Module Replacement (HMR) and optimized build bundles. React Router DOM (v7.7.1) was employed to manage client-side page routing (Home, SignUp, Login, Settings, Profile) with route protection based on authentication state.

4.6 Tailwind CSS and DaisyUI

Tailwind CSS (v4.1.11) is a utility-first CSS framework that allows rapid UI development directly within JSX component markup. DaisyUI (v5.0.50) is a component library built on top of Tailwind CSS that provides semantic component classes (e.g., btn, card, avatar, chat-bubble) and a built-in theme engine. DaisyUI powers the 32 color themes available in the Chatters application, configured dynamically via data-theme attributes on the root container.

4.7 Zustand State Management

Zustand (v5.0.7) is a small, fast, and scalable bear-necessities state-management solution for React. Unlike complex Redux boilerplate, Zustand uses simple hooks for state manipulation without wrapping components in context providers. In Chatters, three centralized stores were implemented: useAuthStore (auth user, checking state, socket connection, online users list), useChatStore (user contacts list, selected chat user, messages array, socket listeners), and useThemeStore (persisted UI theme).

4.8 Cloudinary Cloud Media Storage

Cloudinary is a cloud-based image and video management service that offers media upload APIs, cloud storage, image manipulation, and fast CDN delivery. In Chatters, Cloudinary SDK (v2.7.0) is utilized in backend controllers (auth.controller.js and message.controller.js) to receive base64-encoded image payloads from the frontend, upload them to secure cloud buckets, and return HTTPS CDN image URLs stored in MongoDB.

4.9 JSON Web Tokens (JWT) & Cookie Authentication

JSON Web Token (JWT) is an open standard (RFC 7519) for securely transmitting information between parties as a JSON object. In Chatters, upon successful user signup or login, the backend generates a signed JWT containing the user ID. This token is attached to the HTTP response header as a secure, HTTP-only, SameSite cookie (jwt), protecting the session token from client-side JavaScript access and preventing XSS token theft.

4.10 Postman & API Validation Tools

Postman is an API platform for building, testing, and iterating RESTful APIs. During backend development, Postman was extensively utilized to execute HTTP requests (GET, POST, PUT), verify JSON response schemas, test edge-case input validations, inspect HTTP cookie headers, and debug custom ApiError responses.

6.2 Data Flow and Component Interaction

Data movement within Chatters occurs via two distinct communication channels:

  • 1. RESTful HTTP Channel: Used for synchronous operations such as user signup, login, checkAuth, profile updates, and fetching historic message threads. Client requests pass through Axios instances configured with withCredentials: true. Express routes parse incoming HTTP request bodies and cookies, execute protectRoute middleware verification, and invoke controller functions that interact with MongoDB via Mongoose ODM.
  • 2. Real-Time Socket.io Channel: Used for asynchronous, event-driven real-time operations. Upon authenticated client mount, useAuthStore establishes a WebSocket handshake passing userId in handshake query parameters. The backend stores this mapping in userSocketMap and broadcasts an updated getOnlineUsers array to all sockets. When a user sends a message, the server saves the document to MongoDB, checks if the recipient's socket ID exists in userSocketMap, and immediately emits a newMessage event to the recipient's socket channel.

6.3 Database Schemas and Models

Application data persistence is managed using MongoDB database collections defined by Mongoose schemas:

User Schema (User.js)

  • email: String, required, unique index. Stores user email address.
  • fullName: String, required. Stores full name of the user.
  • password: String, required, minimum length 6. Stores bcrypt hashed password.
  • profilePic: String, default empty string. Stores Cloudinary HTTPS CDN image URL.
  • timestamps: Schema options enabling automatic createdAt and updatedAt ISO timestamp fields.

Message Schema (Message.js)

  • senderId: ObjectId ref User, required. References the sending user document ID.
  • receiverId: ObjectId ref User, required. References the recipient user document ID.
  • text: String, optional. Stores text message payload.
  • image: String, optional. Stores Cloudinary HTTPS CDN image URL for shared media.
  • timestamps: Schema options enabling automatic createdAt and updatedAt ISO timestamp fields.

CHAPTER 7: IMPLEMENTATION AND KEY MODULES

7.1 Implementation Overview

The Chatters platform was implemented following modern full-stack JavaScript software development patterns. The codebase is organized into a modular monorepo structure with distinct backend and frontend directories. The backend utilizes Express.js ES module syntax, asynchronous controller wrappers (asyncHandler), custom error objects (ApiError), and centralized Mongoose database connection scripts (db.js). The frontend uses React 19 functional components with JSX, custom Hooks, and Zustand state stores.

7.2 Key Modules

7.2.1 Authentication & Authorization Module

The Authentication module manages user sign-up, login, session checking, logout, and route protection. Located in backend/src/controllers/auth.controller.js and backend/src/routes/auth.routes.js, it implements:

  • signup (POST /api/v1/auth/signup): Validates required fields, checks for duplicate email addresses in MongoDB, hashes passwords using bcrypt.genSalt(10) and bcrypt.hash(), creates a new User document, generates a JWT cookie via generateToken(userId, res), and returns user JSON data.
  • login (POST /api/v1/auth/login): Verifies user existence by email, compares provided password against stored hash using bcrypt.compare(), generates JWT cookie, and returns user data.
  • logout (POST /api/v1/auth/logout): Clears the HTTP-only jwt cookie by setting maxAge to 0, terminating the user session.
  • protectRoute (Middleware): Middleware function protectRoute extracts the jwt cookie from req.cookies, verifies token authenticity via jwt.verify(), fetches the user document from MongoDB excluding password field (-password), and attaches the user object to req.user.

7.2.2 User Profile & Theme Management Module

This module handles profile picture updates and dynamic UI theme customization:

  • updateProfile (PUT /api/v1/auth/update-profile): Receives base64-encoded image strings from the frontend, uploads them to Cloudinary cloud storage using cloudinary.uploader.upload(), and updates the user's profilePic URL in MongoDB using User.findByIdAndUpdate().
  • Theme Switcher: Managed by useThemeStore on the frontend, which persists selected DaisyUI themes in browser localStorage and updates the root container's data-theme attribute dynamically across 32 supported themes.

7.2.3 Real-Time Messaging & Socket.io Module

The messaging subsystem combines RESTful persistence with real-time WebSocket delivery:

  • getMessages (GET /api/v1/messages/:id): Fetches all messages where (senderId = myId AND receiverId = userToChatId) OR (senderId = userToChatId AND receiverId = myId), returning chronological chat logs.
  • sendMessage (POST /api/v1/messages/send/:id): Processes incoming message payloads containing text and optional base64 image strings. If an image is present, it is uploaded to Cloudinary. The Message document is saved to MongoDB. The controller then retrieves the recipient's socket ID from userSocketMap and emits a real-time newMessage event using io.to(receiverSocketId).emit().

7.2.4 Cloud Media Storage & Image Sharing Module

Media uploads are handled asynchronously via backend/src/lib/cloudinary.js. When a user attaches an image in MessageInput.jsx or ProfilePage.jsx, the file is read into a base64 Data URL string via FileReader. The string is transmitted to Express controllers, which execute Cloudinary SDK API calls. Cloudinary optimizes and hosts the media file on globally distributed CDNs, returning secure HTTPS URLs stored in database fields.

7.2.5 Online Status & Sidebar Module

The presence tracking system operates via backend/src/lib/socket.js. When a client establishes a WebSocket connection, its socket ID is mapped to its user ID in an in-memory userSocketMap object ({ userId: socketId }). The server immediately broadcasts an updated getOnlineUsers array containing all connected user IDs to all sockets. On disconnection, the user ID is removed from userSocketMap and an updated list is broadcast. The frontend Sidebar component consumes this array via useAuthStore to display green online badges and filter online contacts.

7.3 Overall Implementation Flow

The overall application workflow can be summarized as follows:

CHAPTER 9: RESULTS AND DISCUSSION

The completed Chatters real-time messaging application successfully satisfied all defined functional and architectural requirements. Empirical evaluations conducted during local execution and cloud testing demonstrated strong performance characteristics across key operational metrics:

  • Instant Messaging Latency: Real-time bi-directional message transmission via Socket.io demonstrated an average end-to-end latency of under 50 milliseconds on local network environments and under 180 milliseconds when deployed on cloud infrastructure (Render). Messages appeared instantly in active chat threads without page reloads.
  • Robust Authentication Security: HTTP-only JWT cookies effectively secured user session tokens against XSS attacks. Unauthenticated requests to protected backend routes were reliably intercepted by protectRoute middleware and rejected with appropriate HTTP status codes.
  • Efficient Cloud Media Delivery: Base64 image encoding and Cloudinary SDK integration handled media files efficiently. Uploaded images were automatically converted to optimized CDN links, preventing database bloat and ensuring fast client rendering.
  • Accurate Presence Detection: The userSocketMap data structure accurately tracked connected clients. Socket connection and disconnection events triggered real-time getOnlineUsers broadcasts, maintaining synchronous online indicators across all connected client sidebars.
  • Responsive UI & Theme Customization: Zustand state stores provided smooth, reactive UI state transitions without unnecessary component re-renders. The 32 DaisyUI themes allowed instant aesthetic updates persisted across browser restarts via localStorage.

CHAPTER 10: CHALLENGES FACED AND RESOLUTIONS

During the full-stack engineering of Chatters, several technical challenges and integration hurdles were encountered. The table below details these issues along with the specific engineering resolutions adopted.

Challenge / IssueTechnical Problem DescriptionEngineering Resolution Adopted
CORS & Cookie Credentials MismatchBrowsers blocked credentials and JWT cookies during cross-origin requests between Vite dev server (port 5173) and Express backend (port 5001).Configured Express cors middleware with origin: 'http://localhost:5173' and credentials: true. Added withCredentials: true to Axios client instance.
XSS Security & Token Storage VulnerabilityStoring JWT tokens in localStorage exposed user sessions to malicious XSS script extraction.Refactored authentication logic to generate tokens in backend utils.js and set HTTP-only, secure, SameSite cookies (jwt), preventing client JavaScript access.
Large Payload Crashes on Image UploadsTransmitting large base64 image strings caused Express body-parser 'PayloadTooLargeError' crashes.Configured express.json({ limit: '10mb' }) middleware in index.js to support base64 image strings prior to Cloudinary cloud upload.
Stale Socket Connections & Memory LeaksClosing browser tabs without explicit logout left stale user socket mappings in memory.Implemented socket.on('disconnect') event listeners in backend/src/lib/socket.js that delete userId from userSocketMap and broadcast updated online user lists.
Zustand Duplicate Listener BindingRe-subscribing to Socket.io events on component re-renders caused duplicated incoming message rendering.Created explicit subscribeToMessages and unsubscribeFromMessages actions in useChatStore, using socket.off('newMessage') during cleanup.
Production Static Asset RoutingDeploying monorepo frontend and backend together resulted in 404 errors on React Router page refreshes.Added Express static middleware (express.static) serving frontend/dist and catch-all route (app.get('/^(?!\/api).*/')) in backend index.js.
